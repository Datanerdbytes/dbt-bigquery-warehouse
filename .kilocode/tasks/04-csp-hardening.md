## Issue to Verify
A static bundle is not inherently unsafe, and adding CSP does not make malicious trusted script content safe. Audit the current response headers and script loading first. The goal is to constrain script execution and reduce injection risk while preserving required auth and Dash behavior.

## Requirements
1. Inventory Flask-rendered login/signup/callback pages, landing/showcase templates, Dash's generated HTML, inline bootstrap/config/client-side callbacks, external scripts, styles, connections, and dynamically loaded chunks. Read existing public/runtime Supabase configuration; never expose server secrets.
2. Set CSP through the existing Flask response lifecycle, covering intended HTML responses and error paths. Preserve auth installation order, cookies, no-store headers, exact-Origin mutation checks, response codes, and authorization before data loaders run. Do not assume template edits alone protect Dash's generated HTML.
3. Implement a least-privilege script policy using per-response cryptographically unpredictable nonces or validated hashes as appropriate. A nonce must match the actual authorized script elements, be fresh between responses, and never come from user input or a fixed configuration value. Do not indiscriminately nonce every user-supplied script.
4. Account for trusted dynamically loaded scripts and Dash client-side code using mechanisms supported by the installed version. Verify hash/nonce coverage after dependency upgrades and builds. Do not substitute blanket `unsafe-inline`, `unsafe-eval`, wildcard hosts, or unrestricted HTTPS sources simply to make the app render. If installed Dash requires an exception, report the exact path and decision rather than claiming strict CSP was achieved.
5. Limit non-script directives based on observed requirements, including `object-src`, `base-uri`, framing, forms, and connections. Preserve legitimate Supabase session refresh and OAuth behavior; allow only required origins. A script exception must not be hidden inside an unrelated style exception.
6. Ensure headers and document nonces remain paired and nonce-bearing HTML is not reused in a way that breaks freshness. Preserve existing private/no-store rules; do not introduce a shared HTML cache.
7. Report-only mode may be used during local diagnosis, but it is not enforcement. If broad dashboard enforcement is blocked, explicitly document route coverage and the unresolved compatibility requirement. Do not silently call partial/report-only coverage complete.
8. Add offline Flask response tests and real-browser local tests with mocked Supabase/data. Prove an injected unapproved inline script is blocked, an authorized script executes, nonce values differ across responses, and required auth/dashboard behavior works. Verify the policy applied by the browser rather than checking only that a header string exists.

## Acceptance Criteria
- Enforced CSP covers the intended HTML routes and uses tested nonce/hash allowances; route-specific limitations are explicit.
- Unauthorized injection fixtures are blocked while authorized auth bundles, Dash bootstrap/chunks, graphs, client-side callbacks, and navigation continue to work.
- Auth synchronization, refresh, sign-out, OAuth error recovery, and required authorization checks still pass without production queries or real accounts.
- Any tracked auth bundles are rebuilt from source and included consistently. No broad script-policy bypass is added to hide a compatibility issue.
